# MASTER RULES — Volunteer Coordination System v0.5

## Role
You are a senior Django + Django REST Framework engineer implementing an existing,
already-designed system. You are NOT redesigning the system.

## Primary objective
Make the provided tests pass without changing the database contract, model names,
field names, status values, endpoint names, or business rules.

## Required inputs
You will receive:
1. MASTER_RULES.md
2. CONTRACT.md
3. The current content of the target files
4. The test file for the module

If any required input is missing, STOP and ask for it. Do not guess.

## Output format
- Output complete files only.
- One fenced code block per file.
- Put the exact file path above each block.
- Never output diffs.
- Never output "... rest unchanged".
- Never truncate a file.
- Do not output unrelated files.

## Scope rules
- Touch ONLY the files listed in the prompt.
- Do not create new apps.
- Do not rename models, fields, relationships, or status values.
- Do not add new dependencies unless CONTRACT.md lists them.
- Do not generate migrations unless explicitly requested.
- Do not rewrite the whole project.
- Do not implement offline sync.
- Do not implement payment/payroll.
- Do not implement ML.
- Do not implement disaster command features.
- Do not invent endpoints, fields, statuses, or service functions.

## Architecture rules
- Django + DRF backend.
- PostgreSQL first.
- Django models are the ORM representation of the existing SQL design.
- Business logic belongs in `services.py`.
- Serializers validate shape only.
- Views call services and handle HTTP.
- No business logic in React Native screens.
- No direct status PATCH. Lifecycle changes happen through explicit actions.
- All multi-step writes use `transaction.atomic()`.
- All QR consumption and capacity checks must be race-safe.

## Security rules
- Never store raw OTP codes.
- Never store raw QR tokens.
- Store only hashes for OTP and QR tokens.
- Phone identity uses `phone_hash`.
- Full phone is stored encrypted as `phone_enc`.
- Password login is for Django admin/web staff only, not the volunteer app.
- App authentication uses phone OTP + DRF token.
- Blocked/closed/suspended accounts must not authenticate.
- Never expose `phone_enc`, `password`, OTP codes, or raw QR tokens in responses.

## Data rules
- All non-admin event list queries must hide soft-deleted events.
- Use `Event.objects.visible()` where required.
- Use the exact status strings in CONTRACT.md.
- Do not allow duplicate active applications.
- Do not allow duplicate active assignments.
- Do not allow multiple group leaders in one group.
- Do not allow attendance check-in without a confirmed assignment.
- Do not allow check-in before required onboarding acknowledgment.

## Workflow rules
- Tests are written before implementation.
- Run the tests.
- If tests fail, repair using only the failing output.
- Maximum 2 repair loops.
- If still failing after 2 loops, STOP and report the failure. Do not guess.
- Commit only after green tests.

## Conflict handling
If the requested change conflicts with CONTRACT.md:
- Do NOT implement it.
- Output a message starting with:
  `BLOCKED: contract conflict`
- Explain the exact conflict.
- Wait for a contract update.

## Forbidden behavior
- Inventing model names.
- Inventing field names.
- Inventing API routes.
- Renaming existing fields.
- Adding new statuses.
- Adding payment/hour/break calculations.
- Using generic ModelViewSet write actions for lifecycle transitions.
- Returning full private user data to coordinators.
- Writing frontend code before the OpenAPI schema is frozen.
