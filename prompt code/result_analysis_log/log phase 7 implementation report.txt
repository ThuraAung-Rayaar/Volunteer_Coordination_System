## 1. Overall Assessment

The Phase 7 implementation provides solid fundamentals for the operational volunteer check-in engine:
- The integration with PostgreSQL's stored procedure `geo_check_in()` in [geo_service.py](file:///c:/Users/USER/Documents/INTERN/Project/Volunteer%20HR%20Management/python%20stack/backend/services/geo_service.py) is well-structured, parameterised safely, and correctly handles all 13 standard database return codes (`GEO_OK`, `GEO_OUT_OF_BOUNDS`, `GEO_MOCK_SUSPECTED`, etc.).
- Append-only telemetry to `attendance_geo_attempts` is preserved.
- QR token cryptographic hashing (HMAC-SHA256) and nonces comply with the specification.

However, the implementation exhibits **critical concurrency, transaction boundary, and audit context deficiencies**:
1. `select_for_update()` is called outside an atomic transaction block in `attendance_service.manual_check_in`, which violates `BR-TX-01` and Django concurrency requirements.
2. Multi-step mutations (such as QR token consumption paired with application creation) lack an outer transaction wrapper, risking partial commits.
3. PostgreSQL session context is omitted during onboarding acknowledgment, bypassing trigger identity validation.
4. Test coverage is insufficient (only 30 high-level tests, omitting direct database trigger verification, exclusion constraint tests, and rollback tests).

**Acceptance Status:** **NEEDS CORRECTIONS (DO NOT PROCEED TO PHASE 8 BEFORE REMEDIATION)**

## 2. Findings by Severity

### CRITICAL

1. **`select_for_update()` Outside `@transaction.atomic` in Manual Check-In:**
   - **Location:** [backend/services/attendance_service.py#L25-L65](file:///c:/Users/USER/Documents/INTERN/Project/Volunteer%20HR%20Management/python%20stack/backend/services/attendance_service.py#L25-L65)
   - **Problem:** `manual_check_in()` calls `Attendance.objects.select_for_update().filter(...).first()` without an enclosing `@transaction.atomic` decorator or context manager. In Django with autocommit, calling `select_for_update()` outside of a transaction can raise `TransactionManagementError` and provides zero concurrency lock protection.

2. **Partial Commit Vulnerability in Multi-Step QR Redemption:**
   - **Location:** [backend/services/qr_service.py#L90-L150](file:///c:/Users/USER/Documents/INTERN/Project/Volunteer%20HR%20Management/python%20stack/backend/services/qr_service.py#L90-L150)
   - **Problem:** In `redeem_qr_token()` with `action == "join_event"`, the service calls `consume_qr_token()` followed by `EventApplications.objects.create(...)`. Because this is not wrapped in an atomic transaction, if the application creation fails (e.g. unique constraint or database trigger error), the token remains consumed in the database while no application or attendance record is generated.

### HIGH

1. **Missing `@transaction.atomic` Across Mutating Service Operations:**
   - **Locations:**
     - [backend/services/onboarding_service.py](file:///c:/Users/USER/Documents/INTERN/Project/Volunteer%20HR%20Management/python%20stack/backend/services/onboarding_service.py): `acknowledge_event_onboarding`
     - [backend/services/qr_service.py](file:///c:/Users/USER/Documents/INTERN/Project/Volunteer%20HR%20Management/python%20stack/backend/services/qr_service.py): `create_event_qr_token`, `revoke_event_qr_token`
     - [backend/services/attendance_service.py](file:///c:/Users/USER/Documents/INTERN/Project/Volunteer%20HR%20Management/python%20stack/backend/services/attendance_service.py): `check_out`, `confirm_attendance`, `reject_attendance`
   - **Problem:** In `confirm_attendance` and `reject_attendance`, the service runs `cursor.execute("SELECT set_config('app.user_id', %s, true)")`. The parameter `true` sets the setting for the local transaction block only. Without an enclosing `@transaction.atomic`, the variable does not persist for subsequent queries or can bleed across pooled connections.

2. **Missing PostgreSQL Session Context in Onboarding Acknowledgment:**
   - **Location:** [backend/services/onboarding_service.py#L30-L50](file:///c:/Users/USER/Documents/INTERN/Project/Volunteer%20HR%20Management/python%20stack/backend/services/onboarding_service.py#L30-L50)
   - **Problem:** The trigger `trg_01_onboarding_before_insert` enforces `app_user_id() IS NOT NULL AND app_user_id() <> NEW.user_id`. `acknowledge_event_onboarding` does not invoke `set_db_session_context(user.id)`, failing to provide session identity for trigger enforcement.

3. **Missing DB Trigger & Constraint Verification in Test Suite:**
   - **Location:** [backend/apps/attendance/tests/test_phase7.py](file:///c:/Users/USER/Documents/INTERN/Project/Volunteer%20HR%20Management/python%20stack/backend/apps/attendance/tests/test_phase7.py)
   - **Problem:** The test suite contains only 30 basic endpoint tests. It lacks tests for:
     - `trg_01_onboarding_append_only` (ensuring UPDATE / DELETE raise exceptions)
     - `trg_01_onboarding_before_insert` (ensuring users cannot acknowledge for others)
     - `trg_01_attendance_guard` (preventing illegal status transitions)
     - `trg_01_geo_attempts_no_delete` (immutability of geo attempts)
     - `excl_attendance_active_window` (preventing overlapping active attendance windows)

## 4. Recommended Corrections

1. **Apply `@transaction.atomic` across all mutating methods:**
   Ensure each mutation in `attendance_service.py`, `qr_service.py`, and `onboarding_service.py` runs inside an atomic transaction.
2. **Context Session Tracking:**
   Call `set_db_session_context(user.id)` inside `acknowledge_event_onboarding()` so that PostgreSQL trigger `trg_01_onboarding_before_insert` can properly authenticate the acknowledging user.
3. **Database Exception Sanitization:**
   Catch and translate database exceptions with `translate_db_exception(exc)` across all services.
4. **URL Compatibility:**
   Register event-scoped URL patterns in `bff/checkin/urls.py`.
5. **Comprehensive Trigger & Rollback Tests:**
   Create `backend/apps/attendance/tests/test_db_triggers_phase7.py` and expand `test_phase7.py`.
