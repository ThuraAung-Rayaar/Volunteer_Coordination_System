# Phase 6 Implementation Review: Recruitment Applications & Smart Assignment Engine

**Feature / Service:** Phase 6: Recruitment Applications & Smart Assignment Engine (`backend/services/application_service.py`, `backend/services/assignment_service.py`, `backend/bff/volunteer/`, `backend/bff/coordinator/`)  
**Report Artifact:** [`prompt code/prompt_result_analysis/phase6_implementation_review.md`](file:///c:/Users/USER/Documents/INTERN/Project/Volunteer%20HR%20Management/python%20stack/prompt%20code/prompt_result_analysis/phase6_implementation_review.md)

## 1. Overall Assessment

Phase 6 implements the recruitment applications and smart assignment engine spanning Domain 8 (Recruitment Applications) and Domain 9 (Smart Assignment Engine), covering Business Rules `W64`–`W95`.

The core implementation correctly honours the **Database-First** design pattern:
* Algorithmic assignment matching (`run_auto_assignment`, `assign_manually`, `create_assignment_from_application`) lives entirely in PostgreSQL stored procedures. Python services do not reimplement capacity math, skill filtering, or assignment matching in application code.
* Hard integrity constraints (`uq_event_application_active`, `uq_assignment_active`, `uq_assignment_application`, `ex_assignments_no_overlap`) are enforced by the PostgreSQL schema and triggers.
* Privacy tiers (`BR-PRIV-T1`, `BR-PRIV-T2`) are properly respected: `get_event_applications()` provides a minimal profile for pending/rejected applicants (T1 minimal), while disclosing operational capability data (`skills`, `physical_ok`, `can_lift_heavy`, etc.) strictly for accepted volunteers (T2).
* Masked 404 access control (`ResourceMaskedNotFound`) prevents enumeration of applications and event rosters by unauthorized volunteers.

However, several architectural gaps, missing transaction boundaries, and missing test layers must be addressed before Gate P6 sign-off.

### HIGH (2 Findings)

#### [H-01] Missing Transaction Boundaries (`@transaction.atomic`) on Mutating Service Functions
* **Affected Files:**
  * [`backend/services/application_service.py`](file:///c:/Users/USER/Documents/INTERN/Project/Volunteer%20HR%20Management/python%20stack/backend/services/application_service.py)
  * [`backend/services/assignment_service.py`](file:///c:/Users/USER/Documents/INTERN/Project/Volunteer%20HR%20Management/python%20stack/backend/services/assignment_service.py)
* **Details:**
  None of the mutating functions in `application_service.py` (`apply_to_event`, `withdraw_application`, `_decide_application`) or `assignment_service.py` (`run_event_auto_assignment`, `assign_volunteer_manually`, `create_assignment_from_accepted`, `confirm_assignment`, `cancel_assignment`) are wrapped in `@transaction.atomic`.
* **Impact:**
  PostgreSQL triggers execute cascading operations (e.g., auto-assignment on acceptance, cancelling active assignments and attendance on withdrawal, updating post capacity). Without explicit `@transaction.atomic`, exceptions raised midway can leave the database connection unmanaged outside a clean atomic block. In `run_event_auto_assignment()`, the procedure executes and then queries statistics across multiple tables; these should execute within the same atomic transaction.
* **Correction:**
  Decorate all state-mutating service functions with `@transaction.atomic`.

---

#### [H-02] Incomplete Coordinator Invite Workflow (`invite_volunteer_to_event`)
* **Affected File:** [`backend/services/application_service.py`](file:///c:/Users/USER/Documents/INTERN/Project/Volunteer%20HR%20Management/python%20stack/backend/services/application_service.py)
* **Details:**
  The specification mandates `invite_volunteer_to_event(actor, event_id, volunteer_user_id, post_id=None, note="")`. In the current `apply_to_event(user, event_id, post_id, source="browse", ...)` implementation:
  ```python
  if source == "invite":
      get_event_for_manager_or_404(user, event_id, require_write=True)
  app = EventApplications(..., user=user, source=source)
  ```
  `user` is both the actor verified as manager and the applicant created in `EventApplications`. The coordinator therefore invites *themselves* rather than the target volunteer.
* **Impact:**
  Coordinators cannot invite volunteers to events (`W64`).
* **Correction:**
  Implement `invite_volunteer_to_event(actor, event_id: int, volunteer_user_id: int, post_id: Optional[int] = None, note: str = "") -> EventApplications` where `actor` is validated as event manager, `user` is resolved from `volunteer_user_id`, and `source="invite"`.
