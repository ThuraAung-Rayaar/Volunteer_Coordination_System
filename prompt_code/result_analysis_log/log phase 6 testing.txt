2. **Coordinator Volunteer Invite (`W67`)**:
   - Implemented `invite_volunteer_to_event(actor, event_id, volunteer_user_id, post_id, note)` with event manager write authorization.
3. **Session Context Propagation for Trigger Actor Check (`W91`, `W93`)**:
   - Injected `set_db_session_context(user.id)` in `confirm_assignment` and `cancel_assignment` to ensure PostgreSQL trigger `trg_01_assignments_before_update` verifies the calling actor without permission errors.
4. **Two-Tier Privacy Segregation (`W71`, `BR-PRIV-T1`, `BR-PRIV-T2`)**:
   - Applications in `pending`, `rejected`, or `waitlisted` status disclose strict **T1 minimal profile data** only.
   - Applications in `accepted` status unlock **T2 capability profile data** (`skills`, `physical_ok`, `can_lift_heavy`, `has_leader_experience`, etc.).
5. **Database-First Smart Matching Delegation (`W76`–`W85`)**:
   - Python code strictly avoids reimplementing the assignment algorithm, matching rules, or capacity counters.
   - Auto-assignment delegates to PostgreSQL `run_auto_assignment(event_id, actor_id)` and `create_assignment_from_application`.
   - Manual placement delegates to PostgreSQL `assign_manually(application_id, post_id, actor_id, group_code, is_group_leader)`.
   - Capacity metrics are authoritatively computed by PostgreSQL views [`v_accepted_unassigned`](file:///c:/Users/USER/Documents/INTERN/Project/Volunteer%20HR%20Management/python%20stack/postgres%20sql/updated_volunteer_coordination_system_Database.sql#L1250) and [`v_event_post_capacity`](file:///c:/Users/USER/Documents/INTERN/Project/Volunteer%20HR%20Management/python%20stack/postgres%20sql/updated_volunteer_coordination_system_Database.sql#L1200).
6. **Owner-as-Monitor Read-Only Guard (`W51`, `W52`)**:
   - When event coordination is delegated, the owner retains read-only access to applications and assignments. Any write attempts return HTTP 403 with `error.code == "owner_monitor_read_only"`.
7. **BFF Routing & Action Endpoints**:
