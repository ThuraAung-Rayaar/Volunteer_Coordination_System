Understood. We will not fix, modify, normalize, or redesign the SQL prototype.

The SQL file `updated_volunteer_coordination_system_Database.sql` is the authoritative technical baseline for the next iteration. The business rules must be written to describe what this particular SQL version actually supports.

This changes the approach slightly:

- The SQL determines the available entities, relationships, constraints, functions, triggers, views and state transitions.
- The business specification provides the intended operational workflows and business meaning.
- Where the specification and SQL differ, we adapt the business-rule declaration to the SQL prototype rather than changing the SQL to satisfy the older specification.
- Django services will orchestrate the existing SQL capabilities, not introduce a competing implementation.

We are treating this as an intentional prototype iteration, not a database correction exercise.

## 5. Service-to-SQL integration contract

This is an important design rule for the entire implementation.

| Service      | SQL integration                                                                      |
| ------------ | ------------------------------------------------------------------------------------ |
| Auth         | `request_otp()`, `verify_otp()`                                                      |
| Availability | `is_user_available()`, `user_has_schedule_conflict()`                                |
| Verification | `recompute_user_verification()`                                                      |
| Coordinator  | `is_approved_coordinator()`, `change_event_coordinator()`                            |
| Event        | `is_event_manager()`                                                                 |
| Event post   | `application_remaining_capacity()`                                                   |
| Application  | ORM operations with database triggers enforcing rules                                |
| Assignment   | `run_auto_assignment()`, `assign_manually()`, `create_assignment_from_application()` |
| QR           | `consume_qr_token()`, `qr_token_status()`, `qr_check_in()`, `qr_walkin_apply()`      |
| Attendance   | `confirm_attendance()`, `reject_attendance()`                                        |
| Geolocation  | `geo_check_in()`                                                                     |
| Maintenance  | The four maintenance functions                                                       |
| Query        | The eleven existing views                                                            |
| Moderation   | Insert into `moderation_actions`, allowing its trigger to apply the action           |

A few rules are especially important:

1. Do not reimplement assignment algorithms in Python if PostgreSQL already provides them.
2. Do not manually change post capacity if SQL triggers maintain it.
3. Do not implement a second attendance state machine in Django.
4. Do not bypass moderation triggers by directly updating user or event status.
5. Do not calculate GPS acceptance using a client-provided distance.
6. Do not write audit logs independently when the SQL triggers already create them.

## 9. How we will declare each business rule

Every business rule should follow one consistent template.

For example:

## BR-ASSIGN-001 — Volunteer schedule conflict prevention

Assignment domain

SQL enforced

Business objective

Prevent volunteers from being assigned to conflicting event schedules.

Actor

System / authorized coordinator.

Preconditions

- Volunteer has an accepted application.
- Event and post are valid.
- Assignment operation is authorized.

Business rule

A volunteer must not receive an assignment that conflicts with another applicable assignment.

System execution

1. Receive assignment request.
2. Validate actor authorization.
3. Invoke the appropriate assignment workflow.
4. PostgreSQL evaluates scheduling and assignment constraints.
5. Return success or a structured business error.

SQL references

- `user_has_schedule_conflict()`
- `is_user_available()`
- Assignment triggers.
- `assignments` table.

Service responsibility

`assignment_service.py`

Expected outcomes

- Success: assignment created.
- Failure: database rejects the conflicting operation.

Test scenarios

- Assign a volunteer with no conflicting schedule.
- Attempt an overlapping assignment.
- Attempt an assignment outside declared availability.
- Attempt unauthorized manual assignment.

This is how we will make the business specification directly implementable.

Implement the business logic and orchestration.

Verify the complete system against its business rules.

My recommendation: Start with Document 1, the complete Business Rules Declaration. It should cover all 18 SQL-aligned domains, derive its rules from the 22 tables and their associated functions, triggers and views, and preserve the intended workflows from the v0.5.2 specification wherever they are supported.

Once that document is approved, we move to the service architecture. That way, we have a clear contract for every service before writing its implementation.

No SQL changes are part of this plan.
